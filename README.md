## 项目概述

本项目是一个基于大语言模型和 RAG（Retrieval-Augmented Generation）架构的企业级智能客服系统，实现了从用户提问、意图判断、知识检索到生成回答的完整 AI 对话链路。

**核心能力**：

- **Agentic RAG**：使用 LangGraph 构建的 Agent 自主判断是否需要检索知识库，避免无关问题浪费 API 调用
- **混合检索**：Dense（语义）+ Sparse（关键词）双路检索 + RRF 融合排序，兼顾语义理解和关键词匹配
- **流式输出**：基于 SSE（Server-Sent Events）实现逐字流式输出，提升用户体验
- **多知识库路由**：支持创建多个知识库，Agent 根据问题自动路由到最相关的知识库
- **多轮对话**：基于 LangGraph Checkpointer 持久化对话状态，支持上下文连贯的多轮问答
- **用户反馈系统**：支持点赞/点踩评价（含可选文字备注），帮助评估回答质量

## 技术选型及原因

### 为什么选择 DeepSeek V4 Flash + OpenAI 兼容接口？

| 选项                      | 选择理由                             |
| ----------------------- | -------------------------------- |
| **OpenAI GPT-4o**       | 效果好但成本高，不适合学生项目                  |
| **通义千问 API**            | 有免费额度，但模型能力一般                    |
| **本地 Ollama**           | 需 GPU 资源，部署复杂                    |
| **✅ DeepSeek V4 Flash** | 性价比极高，通过 OpenAI 兼容接口接入，代码零修改即可切换 |

使用 OpenAI 兼容接口的核心优势是**接口标准化**——任何提供 OpenAI 兼容 API 的模型都可以通过修改 `.env` 配置快速切换，无需修改代码。

### 为什么选择 Qwen3-Embedding-8B（4096 维）？

| 选项                       | 维度       | 中文表现   | 成本                  |
| ------------------------ | -------- | ------ | ------------------- |
| text-embedding-3-small   | 1536     | 一般     | 付费                  |
| text-embedding-3-large   | 3072     | 一般     | 较贵                  |
| **✅ Qwen3-Embedding-8B** | **4096** | **优秀** | **免费（SiliconFlow）** |

Qwen3-Embedding-8B 是阿里巴巴最新开源的嵌入模型，在中文语义理解上表现优秀，4096 维的高维度能编码更丰富的语义信息，且 SiliconFlow 平台提供免费额度。

### 为什么选择 Qdrant（而非 Chroma / Faiss）？

| 选项           | 混合检索                        | 部署复杂度         | 性能    |
| ------------ | --------------------------- | ------------- | ----- |
| Chroma       | 不支持原生混合检索                   | 低（文件模式）       | 一般    |
| Faiss        | 需额外部署稀疏检索                   | 低（文件模式）       | 好     |
| **✅ Qdrant** | **原生 Dense + Sparse + RRF** | **中（Docker）** | **好** |

Qdrant 的原生混合检索能力是核心选型理由：它内置了稠密向量检索和 BM25 稀疏向量检索，并通过 RRF（Reciprocal Rank Fusion）进行融合排序。这意味着无需额外部署 Elasticsearch 或单独管理关键词索引，一套系统即可完成语义检索和关键词检索。

### 为什么选择 LangGraph（而非直接调用 LLM API）？

| 方案              | Agentic RAG | 流式输出                | 状态管理             | 工具调用     |
| --------------- | ----------- | ------------------- | ---------------- | -------- |
| 直接调用 LLM API    | 自行实现        | 自行实现                | 自行实现             | 自行实现     |
| LangChain       | 基础支持        | 支持                  | 有限               | 支持       |
| **✅ LangGraph** | **原生支持**    | **astream\_events** | **Checkpointer** | **原生支持** |

LangGraph 提供了：

1. **Agent 编排**：Agent 可自主决定调用工具（检索知识库）的时机和次数
2. **`astream_events`**：细粒度的流式事件，包括 token、tool\_start、tool\_end 等
3. **Checkpointer**：内置对话状态持久化到 MySQL，支持多轮对话恢复
4. **工具系统**：通过 `@tool` 装饰器即可将任意函数包装为 Agent 可用工具

## 整体 AI 架构

### RAG 链路图（简化版）

```text
用户提问
    │
    ▼
┌─────────────────────────────────────────────┐
│              LangGraph Agent                 │
│                                              │
│   ┌──── → LLM 判断是否需要检索? ────┐        │
│   │         │          ↑            │        │
│   │    需要检索        │            │        │
│   │         │         │            │        │
│   │         ▼         │            │        │
│   │   retrieve_knowledge tool       │        │
│   │         │                      │        │
│   │         ▼                      │        │
│   │   embed(query) ──→ Qdrant      │        │
│   │         │        Dense+Sparse  │        │
│   │         │        +RRF          │        │
│   │         ▼                      │        │
│   │   格式化检索结果 ←──────────────┘        │
│   │         │                               │
│   └──── ← 注入结果到 LLM                     │
│              │                              │
│              ▼                              │
│         生成回答 (流式 token)                │
└─────────────────────────────────────────────┘
                    │
                    ▼
              SSE 流式输出到前端
                    │
                    ▼
              用户看到逐字回答
```

### 知识库处理流水线

```text
上传文档 → 保存到磁盘 → 解析（.md / .txt）
    → MarkdownHeaderTextSplitter 按标题分组
    → RecursiveCharacterTextSplitter 二次切分（400 chars/块，50 overlap）
    → Qwen3-Embedding-8B 向量化（批处理 + 重试）
    → Qdrant upsert（同时写入 dense vector + sparse vector）
    → 更新文档状态为 ready
```

### 混合检索策略

```text
查询文本
    │
    ├────→ Dense Path: embed(query) → cosine 相似度搜索 (4096-dim)
    │          score_threshold = 0.7, prefetch top_k*2
    │
    ├────→ Sparse Path: BM25 分词 → TF-IDF 稀疏向量搜索
    │          prefetch top_k*2
    │
    └────→ RRF Fusion: FusionQuery(fusion=Fusion.RRF)
               k=60, final top_k=5
```

## 业务思考：AI 工程问题处理

### 1. 检索为空（No Retrieval）的处理

**问题**：当用户提问的内容不在知识库中时，LLM 可能编造一个看起来合理但实际错误的答案。

**三层防御**：

1. **System Prompt 层**：明确要求"如果知识库中没有相关信息，说'抱歉，我暂时无法回答这个问题'"
2. **工具返回值层**：`retrieve_knowledge` 检索为空时返回空字符串，LLM 没有素材编造
3. **相似度阈值层**：`score_threshold = 0.7`，低于阈值的弱相关结果直接被过滤，防止"强行使用"

**效果验证方式**：

- 提出一个知识库中不存在的问题，观察 LLM 是否返回兜底话术
- 通过 RAG Eval Pipeline 持续监控空检索场景的表现

### 2. 上下文超长（Context Overflow）的处理

**问题**：多轮对话 + 长文档检索可能导致超出 LLM 的上下文窗口限制，或者关键信息被淹没在大量文本中。

**分层策略**：

| 策略     | 实现方式                      | 效果                  |
| ------ | ------------------------- | ------------------- |
| 分块大小控制 | CHUNK\_SIZE = 400 字       | 每个块精简，减少 token 消耗   |
| 结果数量限制 | top\_k = 5                | 最多 5 条相关片段进入 prompt |
| 提问长度限制 | 用户问题 ≤ 500 字              | 防止问题本身过长            |
| 历史窗口控制 | LangGraph Checkpointer 截断 | 只保留最近 N 轮对话         |
| 分块重叠   | overlap = 50 字            | 相邻块边界信息不丢失          |

### 3. LLM 幻觉（Hallucination）的抑制

**问题**：LLM 可能编造不存在的功能、混淆不同产品的信息、或对不确定的问题给出错误答案。

**多层抑制策略**：

1. **Prompt 设计**：约束"仅根据知识库检索到的内容回答"，"回答时引用具体的文档名称和章节"
2. **检索增强**：确保 LLM 有足够且相关的上下文信息，减少"被迫编造"的可能性
3. **相似度过滤**：低相关度结果不进入 prompt，避免"误导性信息"
4. **Agent 多轮检索**：当首次检索结果不充分时，Agent 可换种表述再次检索，提高信息覆盖率
5. **人工监督**：通过用户反馈机制（like/dislike）收集回答质量数据，持续优化

### 4. Agentic RAG vs 传统 RAG 的设计思考

| 方面     | 传统 RAG          | Agentic RAG（本项目）     |
| ------ | --------------- | -------------------- |
| 检索时机   | 每个问题都检索         | LLM 自主判断             |
| API 调用 | 2 次：Embed + LLM | 0\~N 次：LLM 判断+可能多次检索 |
| 闲聊场景   | 浪费 Embedding 调用 | 直接回应，不检索             |
| 检索不足   | 强制用检索结果         | 可换表述多次检索             |
| 复杂度    | 低               | 较高                   |

**为何选择 Agentic RAG**：

- 避免"每次都要检索"的无差别开销
- 闲聊/问候类问题直接回应，减少 API 调用
- 如果检索结果不够充分，LLM 可以换一种问法再次检索，比固定检索更灵活

### 5. 大规模知识检索下的 LLM 执行保障

**问题**：当知识库文档非常多时，检索返回的相关片段可能有数十条甚至更多，LLM 面对大量上下文可能：

1. **注意力稀释**：遗漏某条关键规则
2. **信息过载幻觉**：编造不存在的规则或混淆不同规则

**设计方案**（已实现部分 + 待完善方向）：

#### 已实现

1. **分库路由**：将文档按主题划分到不同 knowledge\_base，Agent 根据 KB 描述判断应该检索哪个
2. **top\_k 限制 + score\_threshold 过滤**：严格控制进入 LLM 的片段数量和质量
3. **RRF 融合排序**：混合检索的天然信息蒸馏机制，从大量候选中选出最相关的 K 个
4. **Agent 分段检索**：Agent 可多次调用工具，从不同角度覆盖知识需求

#### 完善方向（如需进一步保障）

1. **分层摘要**：当检索结果 > 10 条时，先对结果按来源文档进行分组摘要，将摘要而非原文注入 LLM
2. **规则优先级排序**：在知识库元数据中标注文档的重要性等级，检索结果按"高优先级 → 低优先级"排序呈现
3. **分步校验**：当回答涉及多条规则时，让 LLM 逐个确认每条规则的来源，而非一次性生成

### 6. 频率控制与异常处理

- **每日限额**：每用户每日最多 100 次对话（可配置），内存计数 + 定期磁盘持久化
- **Embedding 重试**：API 调用失败时最多重试 2 次，间隔 1 秒
- **后台任务隔离**：每个对话在独立的 asyncio.Task 中运行，异常不影响其他对话
- **优雅关闭**：应用关闭时取消所有运行中的 Agent 任务，关闭数据库连接

### 对 AI 生成代码的优化和修正

在构建 RAG 链路时，对 AI 生成的代码做了以下关键优化和修正：

| 优化项           | AI 初始版本      | 实际优化后的方案                        |
| ------------- | ------------ | ------------------------------- |
| **检索策略**      | 仅使用 Dense 检索 | 改为 Dense + Sparse 混合检索 + RRF 融合 |
| **分块策略**      | 固定长度切分       | 改为 Markdown 标题分组 + 长段落二次切分      |
| **Agent 提示词** | 静态提示词        | 改为动态查询 KB 列表注入提示词               |
| **去重机制**      | 无去重          | 添加 MD5 哈希去重，避免重复嵌入              |
| **并发处理**      | 串行 Embedding | 改为 asyncio.gather 批处理           |
| **频率限制**      | 无限制          | 添加每日调用计数 + 磁盘持久化                |
| **反馈系统**      | 简单 CRUD      | 改为 toggle 模式：相同 → 取消；不同 → 切换    |
| **异常处理**      | 捕获后忽略        | 逐层传递 + SSE error 事件通知前端         |
| **日志系统**      | print 调试     | 规范化的 logging + 彩色控制台输出          |

**具体例子**：

1. **混合检索的改进**：AI 初始只生成了简单的向量检索。经过分析，我发现单纯依赖语义检索在精确匹配产品名称时效果不佳，于是增加了 BM25 稀疏检索通道，并用 RRF 融合排序。这显著提升了对"Auperator"等专有名词的检索准确率。
2. **分块策略的优化**：AI 默认使用了固定字符长度的文本切分。我将其改为先按 Markdown 标题（`##` / `###`）分 section，再对长 section 二次切分。这样每个 chunk 的 metadata 中保留了章节信息，LLM 回答时能准确引用来源。
3. **并发 Embedding 的优化**：AI 初始版本逐条处理向量化，耗时较长。改为 `asyncio.gather` 批量并行处理后，知识库初始化速度提升了 5-10 倍。
4. **去重机制的添加**：AI 初始没有文件去重逻辑，多次运行 `init_kb` 会重复写入。添加了 MD5 哈希比较后，实现了幂等初始化。

### RAG 回答质量的评估方式

当前主要通过以下方式评估：

1. **人工测试**：准备了一组测试问题（涵盖产品功能、故障排查、无关闲聊三类），每次修改 Prompt 或检索参数后手工验证回答质量
2. **RAG Eval Pipeline**（`app/scripts/rag_eval.py`）：自动化运行测试集，输出结构化的评估结果，对比不同配置下的表现
3. **用户反馈收集**：通过 like/dislike 机制收集真实用户的评价，作为长期优化依据

**评估重点**：

- 检索是否命中了正确的知识片段
- LLM 的回答是否准确引用了检索内容
- 空检索场景是否触发了兜底话术
- 引用来源是否正确展示
