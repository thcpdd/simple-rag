## 关键发现与问题

### 🚩 发现一：跨知识库检索干扰严重

**最严重的问题。** Auperator 领域的 10 个问题中，绝大多数检索结果都混入了 snatcher（智能抢课系统）的文档，且这些无关文档往往排名很高（甚至第一）。

```
Q1 "Auperator" → top-1 是 snatcher/core.md
Q2 "DeepAgents" → top-1 是 snatcher/backend.md
Q4 "事件系统" → top-1 是 snatcher/mail.md
Q6 "记忆服务" → top-5 全部是 snatcher
Q7 "Vector" → top-5 全部是 snatcher
```

**根因**: `search()` 函数在所有 Collection 中检索，没有按知识库域过滤。Qdrant 只有一个 `simplerag` Collection，Auperator 和 snatcher 的文档都混在一起。

**建议**:
- 在 Qdrant payload 中加入 `kb_name` 字段
- 检索时根据对话上下文判断所属知识库，加 `must` filter
- 或者在 `retrieve_knowledge` 工具中增加 `kb_name` 参数

### 🚩 发现二：部分 Auperator 文档无法被检索到

Q6（记忆服务）本应命中 `auperator/docs/backend/services/memory.md`，Q7（Vector）本应命中 `vector.yaml` 相关文档——但这些文档完全没有出现在检索结果中。

可能原因：
- 文档内容较短，embedding 效果差
- chunk 分割方式导致信息碎片化
- RRF 融合排序被 snatcher 的高频关键词压低了排名

**建议**: 检查 `init_kb` 对这些文档的分块和嵌入结果，确认 chunk 质量。

### 🚩 发现三：Auperator Q1-5 检索相对较好，Q6-10 检索严重失败

Auperator 问题呈明显两级分化：
- Q1-Q5：README.md 和架构文档检索到了基本信息（Precision ~0.4）
- Q6-Q10：`services/` 子目录下的文档几乎完全未被命中（Precision ~0.1）

说明 `knowledge/auperator/docs/backend/services/` 下的文档分块可能存在质量问题。

### 🚩 发现四：Agent 在检索不足时依赖 LLM 自身知识

Q2（DeepAgents）、Q3（Drain3）、Q6（记忆服务）中，检索结果严重不足，但 LLM 仍然生成了详细且基本正确的回答。这既是优点（提供有用回答）也是缺点（非 grounded）：

- Q2 甚至列出了不在 ground_truth 中的 "initialize" Agent
- Q3 的 Detailed 配置参数在检索结果中不存在
- 回答看起来很专业，但无法保证准确性

### ✅ 发现五：Snatcher 领域检索质量优异

智能抢课系统的 10 个问题整体 Precision 达到 0.66，上下文充分性 4.2。snatcher 目录下的 markdown 文档结构清晰、内容针对性强、有明确的问答导向。

这说明 **知识库文档质量直接影响 RAG 效果**。Snatcher 文档是功能模块文档，每个文件聚焦一个模块；而 Auperator 文档更偏项目文档风格。

---

## 改进建议（按优先级排序）

### P0 - 紧急
1. **按知识库域过滤检索**：在 Qdrant payload 加 `kb_name`，检索时加 `must` filter，解决跨域干扰问题
2. **检查 services/ 子目录的 chunk 质量**：确认 `memory.md`、`drain3.md` 等文档是否被正确处理

### P1 - 重要
3. **优化 RRF 融合排序权重**：当前 dense + sparse RRF 融合下，无关文档经常排第一，需调整 prefetch 参数
4. **增加 fallback 机制**：当检索结果与问题语义相似度普遍低于阈值时，引导 LLM 诚实回应"无法回答"

### P2 - 建议
5. **增加 Agent 工具参数**：允许用户在调用 `retrieve_knowledge` 时指定知识库名称
6. **优化文档分块策略**：确保每个知识库文件的 chunk 包含足够的信息量，避免过短的碎片化 chunk

---

*评估方式：人工逐条阅读检索结果和 LLM 回答，对比 ground_truth 进行打分。*
